## A. État des lieux chiffré

### A.1 Séquence de chargement actuelle (lu dans `packages/sdk-browser/`)

Point d'entrée `createExplorer()` (`index.ts:181`) :

1. `loadClusterManifest()` (`manifestLoad.ts:35`) : fetch JSON du pointeur `manifest.json` → fetch JSON `clusters.json` → si manifeste binaire présent, **un seul** `fetch`+`arrayBuffer()` du sidecar `clusters.bin`, chargé **intégralement**, jamais par `Range` (`manifestLoad.ts:52`).
2. `GLTFLoader().loadAsync(source.gltf|scene.gltf)` (`index.ts:203`) : **un seul appel**, fetch interne à Three.js, pas de `Range`. `source.gltf`/`source.bin` sont requis chaque fois qu'au moins une primitive n'est pas en pages autonomes (voir A.2) ; `scene.gltf`/`scene.bin` (triangle factice + textures) seulement si **toutes** les primitives sélectionnées ont des pages autonomes.
3. Couverture racine du DAG (« amorçage ») puis pages à la demande (`createPageStreamer`, `streamingPages.ts:19`) ou préchargement complet (`preload==='all'`, `clusterPages.ts:8`).

Aucun `new Worker` dans `packages/sdk-browser/` (0 résultat, recherche exhaustive) : **tout le décodage tourne sur le thread principal**, y compris le décodage WASM `meshoptimizer` des pages `.wgpg` (`geometryPage.ts:19-22`, appelé depuis `autonomousPages.ts:79`). `GLTFLoader` n'a ni `DRACOLoader` ni `KTX2Loader` configuré : parsing JSON et décodage image 100 % thread principal. `textureMips.ts` ne fait que générer des mips **GPU** après upload (calcul, pas réseau).

Concurrence : pas de limite de connexions explicite, seulement des budgets logiciels — `DEFAULT_PAGE_WORKERS=32` (`index.ts:49`) et `workerCount` dans `createPageStreamer`/`loadClusterPages` (`streamingPages.ts:19,24,71`, `clusterPages.ts:8`) désignent un nombre de **requêtes concurrentes**, pas des `Worker` réels (aucun thread) ; `maxTransferBytes=8 Mio` (`streamingPages.ts:19,73`) borne les octets en vol, pas le nombre de requêtes.

**N'existe pas** dans `sdk-browser` : en-tête `Range`/`Content-Range`, `DecompressionStream`/gzip/brotli/zstd, Cache Storage/OPFS/IndexedDB (0 résultat chacun, recherche exhaustive). Seule « compression » : le format binaire `meshopt` lui-même.

### A.2 Format compilé (lu dans `packages/asset-compiler-rust/src/`)

- `clusters.bin` : **un seul fichier** par cache, en-tête 16 o (`WGMB`, version, columnCount, réservé) + table de 20 colonnes (offset, longueur) alignées sur 8 o (`manifest_binary.rs:12-27`). Exemple du contrat documenté (`docs/FORMAT.md:46`, scène Emerald Square) : manifeste JSON 48,4 Mo → 387 Ko + sidecar 17,0 Mo.
- DAG : cluster ≤ **128 triangles** (`dag.rs:19`, `DAG_CLUSTER_TRIANGLES`), ≤ 255 sommets (`dag.rs:21`) ; regroupement de 8 à 32 clusters voisins par niveau, simplification à verrous de sommets partagés.
- Chaque cluster est adressé **deux fois** : objet SHA-256 individuel `objects/{sha}.bin` (indices bruts, `lib.rs:572`) **et** concaténé avec offset dans un bundle `.wgsb` (`lib.rs:566-586`) — redondance de stockage confirmée par lecture directe.
- Cible de bundle : `STREAM_BUNDLE_BYTES=131072` (128 Kio, `lib.rs:23`), calculée sur les **indices bruts seulement** (384×4=1536 o/cluster) → jusqu'à ~85 clusters avant d'atteindre la cible. **Aucune constante « 42 Ko » ni « 30 clusters » n'existe dans le code** ; ce sont des moyennes observées ou une estimation erronée du brief, pas une valeur codée. Une constante `CLUSTER_TRIANGLES=256` (`lib.rs:40`) est déclarée et jamais utilisée (code mort, sans lien direct avec le chargement).
- Bundles racines (« pinned ») concaténés **entre primitives d'une même scène** en objets partagés ≤ 1 Mio (`docs/FORMAT.md:72`) — c'est le mécanisme réel d'« amorçage partagé » ; il ne s'étend pas entre scènes ni entre sessions (**pas de cache persistant inter-session**, confirmé par les deux agents).
- Pages géométrie autonomes `.wgpg` (`WGP2`, `geometry_page.rs`) : encodées `meshopt` (`encode_index_buffer`/`encode_vertex_buffer`), mais **sans quantification** — `STRIDE=72` o, tous les attributs en `f32` (« lossless », `geometry_page.rs:7`). Pas d'octaédrique, pas d'UV 16 bits aujourd'hui.
- Adressage par contenu SHA-256 : **existe**, omniprésent (`objects/{sha}.bin|.wgpg|.wgsb`, clé de cache incluant le hash du compilateur lui-même, `lib.rs:46-47,408-409`).
- Compression générique (Brotli/zstd/gzip) : **n'existe pas**, ni côté Rust (`Cargo.toml` : `serde_json, sha2, rayon, memmap2, meshopt` seulement) ni côté client.
- KTX2/Basis : **n'existe pas** dans ce crate (0 résultat `ktx2|basis`) ; le compilateur ne fait que réécrire les URI d'images (`lib.rs:668`).
- `source.bin` : artefact de compilation (bufferViews glTF concatés, non quantifiés) qui sert à régénérer `source.gltf` et la `scene.gltf`/`scene.bin` de secours ; **pas relu par le pipeline clusters/pages**. Mais le runtime le **fetch quand même** dès qu'une primitive n'est pas autonome — cas des matériaux BLEND (verre) : « progressive texture admission and transparent autonomous pages are not implemented » (`docs/FORMAT.md:90`). Explication la plus probable du chargement complet de `source.bin` pour Emerald Square, qui contient du verre.

## B. État de l'art par piste (sources en fin de section)

**1. Fichier unique + `Range` HTTP/2 ou HTTP/3.** HTTP/2 multiplexe plusieurs `Range` sur une connexion unique avec en-têtes compressés ; limite pratique : beaucoup de backends objets n'acceptent qu'une plage par requête, mais un simple serveur de fichiers statiques (Vite, Caddy, nginx) n'a pas cette limite. Gain surtout sur la latence de mise en file (RTT réel), marginal en localhost avec keep-alive HTTP/1.1 déjà actif. **Existe** comme technique standard (RFC 7233, MDN) ; **à prototyper** ici (aucun `Range` ni côté client ni côté format de bundle aujourd'hui).

**2. Compression + décodage hors thread principal.** `DecompressionStream` (Compression Streams API) : supporté depuis Chromium 80, **existe**, prêt à l'emploi. `meshoptimizer` : décodeur WASM 5-7 Ko, ~1 Go/s en SIMD desktop, ratio ~2-4× sommets / ~5-6× indices (par rapport à des données déjà quantifiées) — **existe déjà côté compilateur Rust** (`geometry_page.rs`), mais décodé sur le thread principal côté client (A.1). `EXT_meshopt_compression` est une extension glTF/Khronos standard, utilisée par Cesium 3D Tiles pour des nuages de points massifs. Compression générique (Brotli/zstd) : **n'existe pas** ici, ni serveur ni client.

**3. Cache persistant.** OPFS : Chrome/Edge 86+, Firefox 111+, Safari 15.2+ — **existe**, bien établi. `Cache-Control: immutable` + adressage par contenu : pratique standard (`max-age=31536000, immutable` sur URL hachée). L'adressage SHA-256 des objets **existe déjà** côté format compilé (A.2) ; ce qui manque : en-têtes HTTP adaptés côté serveur et écriture/lecture OPFS ou Cache Storage côté client (aucun des deux trouvé dans `sdk-browser`).

**4. Préchargement prédictif.** Pratique répandue dans les moteurs de jeu open-world : prioriser joueur + environs, puis visible lointain, puis prédit non visible, à partir d'une extrapolation de trajectoire caméra. Aucune API navigateur dédiée — c'est entièrement applicatif. **À prototyper** intégralement ; aucune trace dans le code lu.

**5. Textures KTX2/Basis.** Three.js embarque un `KTX2Loader` (transcodage vers BC/ASTC/ETC2 GPU-natif), réduction mémoire texture typique 4-8×, reste compressé en VRAM (contrairement à un PNG/JPEG décodé en RGBA brut). **Existe côté runtime Three.js** (non branché dans ce SDK : `GLTFLoader` sans `setKTX2Loader`, A.1) ; **n'existe pas** côté compilateur Rust (aucune conversion KTX2, A.2) — pipeline de conversion entièrement à construire. Streaming par mip/visibilité (texture virtuelle) : **à prototyper**, aucune référence dans le code.

**6. Pages de sommets autonomes.** Le format **a déjà** des pages `.wgpg` autonomes, meshopt-encodées, adressées par SHA, avec un mode `scene.gltf` qui évite `source.bin` (A.2) — mais seulement pour les primitives opaques/masquées. Le blocage documenté (« transparent autonomous pages not implemented ») explique directement pourquoi `source.bin` reste sur le chemin critique dès qu'une scène a du verre (Emerald Square). Quantification (positions, normales octaédriques, UV 16 bits) : les algorithmes existent en spécification (`docs/vision/annexes/attributs-et-compression.md` : encodeur/décodeur octaédrique, empaquetage entier zigzag) mais **aucune implémentation Rust ou TS** trouvée — étiqueté explicitement « conception proposée » dans le document lui-même.

**7. Plus loin.** WebTransport : Baseline sur tous les navigateurs majeurs depuis Safari 26.4 (mars 2026), Chrome 97+ — **existe** comme API, **à prototyper** dans ce moteur (aucune trace). Décodage GPU en compute : WebGPU n'a pas de stage *mesh shader* natif ; la décompression de meshlets « à la volée » dans un mesh shader est une technique native (GPUOpen, 2023) transposable en un compute shader WebGPU écrivant dans un buffer de stockage — **à prototyper**, aucun mesh shader ni décodage compute dans le code lu. Format de scène unique streamable : `clusters.bin` **est déjà** un manifeste unique pour la structure géométrique (A.2) ; les textures/`source.bin`/pages restent des fichiers séparés — extension possible mais **à prototyper**, cf. Cesium 3D Tiles / glTF implicite comme référence externe.

## C. Plan de mesures

Méthodologie commune (toutes pistes) : Chrome (Playwright, comme `scripts/headless/`), à froid (cache HTTP vidé via `Network.clearBrowserCache` CDP, pas juste « disable cache ») puis à chaud (rechargement immédiat). Trois chiffres : **(1)** temps jusqu'à la première image complète en niveaux grossiers (couverture racine posée), **(2)** temps jusqu'au détail final (aucune page manquante au budget d'erreur cible), **(3)** octets transférés (`Network.getResponseBody`/somme des tailles de réponse). Rejet si la capture PNG diffère de la référence pixel-identique (hors bruit A/A déjà caractérisé par le protocole de vérité) — aucune piste n'est validée sur une image dégradée.

### Piste 1 — fichier unique + `Range` (détaillé, gabarit pour les pistes suivantes)

- **Prototype minimal** : un script de compilation à part (hors `asset-compiler-rust`, pour ne pas toucher le format existant pendant le prototypage) qui concatène tous les objets `objects/*.wgpg`/`*.bin` d'une scène compilée en un seul blob avec table d'offsets ; un petit serveur statique qui honore déjà `Range` (Vite le fait nativement, à vérifier par une requête `curl -r` réelle plutôt que supposé) ; un chargeur client qui remplace les `N` fetchs par des `fetch(url, {headers:{Range:...}})` ciblés.
- **Serveur HTTP/2 local** : Vite `server.https` bascule automatiquement sur `http2.createSecureServer` avec repli HTTP/1.1 (`allowHTTP1:true`) dès qu'un certificat est fourni — `@vitejs/plugin-basic-ssl` génère et met en cache un certificat auto-signé sans configuration manuelle (confirmé via la doc officielle Vite). Suffisant pour mesurer HTTP/2 en local sans changer d'outillage.
- **Serveur HTTP/3 local** : deux options concrètes, aucune essayée ici. (a) Caddy avec son autorité interne ajoutée au magasin de confiance système, reverse-proxy vers le `dist/` statique du Lab — Caddy négocie h2/h3 automatiquement une fois la confiance établie. (b) Sans vraie infra TLS : lancer Chrome avec `--origin-to-force-quic-on=<host:port>` force QUIC sur une origine donnée pour du test, documenté comme usage prévu par Chromium (flag de développement, pas pour de la prod).
- **Critère de conclusion** : le chiffre (3) octets transférés ne bougera pas (les octets sont les mêmes) ; le test porte sur le nombre de requêtes et le temps (1)/(2). Conclure seulement si le gain persiste avec une latence réseau simulée réaliste (`Network.emulateNetworkConditions`, ≥ 20-50 ms de RTT) — en localhost pur, gain probablement faible ou nul et ne doit pas être extrapolé.
- **Rejet** : capture non identique, ou dégradation de robustesse (temps (2) qui augmente parce que la sérialisation en un seul blob retarde des pages qui arrivaient plus tôt en parallèle).
